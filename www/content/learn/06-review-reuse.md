## 이번 수업에서 배울 내용

완료된 초안과 실제 실행 결과를 구분합니다. 반복 업무에는 무엇을 지침으로 저장하고 무엇을 매번 새 자료로 제공해야 하는지 정합니다.

## 완료라는 말을 단계별로 읽기

| 상태 | 뜻 | 확인할 근거 |
|---|---|---|
| 초안 작성 | 검토할 결과를 만들었음 | 실제 결과 내용 또는 파일 |
| 검토 완료 | 정한 기준으로 결과를 확인했음 | 검토 항목과 수정 내역 |
| 사용자 확인 | 사용자가 결과나 실행 범위를 확인했음 | 해당 요청에 대한 응답 |
| 실행 완료 | 게시·발송·저장 등 요청한 실행이 끝났음 | 실제 서비스 결과·파일·작업 상태 |

파일 링크가 있어도 열리지 않으면 파일 전달은 확인되지 않은 상태입니다. 예약 설정 화면이 있어도 실제 실행한 기록이 없다면 예약 실행 성공을 확인했다고 할 수 없습니다. 초안을 만들었다는 보고와 실제 게시했다는 보고는 각각의 근거가 필요합니다.

## 예제 · 보기 좋은 FAQ에서 잘못된 약속 찾기

가상 정책에는 “결제 확인 후 영업일 2일 이내 출고”가 있습니다. 결과에 “이틀 안에 도착합니다”라고 쓰면 출고와 배송 완료를 혼동한 것입니다. 이때 문장을 다듬는 요청보다 기준을 알려 주는 수정 요청이 효과적입니다.

```text
정책의 2일은 도착 기한이 아니라 출고 기한이야.
그 표현을 고치고 배송 완료 시점은 보장하지 말아 줘.
모든 FAQ에 정책 근거와 확인 필요 항목을 다시 확인해 줘.
```

## 실습 · 결과 검토표 만들기

| 항목 | 확인 방법 | 내 결과 |
|---|---|---|
| 원문 수치 | 문의 6행과 유형 합계 비교 | 직접 기입 |
| 정책 의미 | 출고와 도착 표현 비교 | 직접 기입 |
| 누락 처리 | 결제 정책 누락 표시 확인 | 직접 기입 |
| 개인정보 | 이름·연락처 등이 남았는지 확인 | 직접 기입 |
| 파일 전달 | 다운로드 파일 직접 열기 | 직접 기입 |
| 실행 범위 | 게시·발송 여부 확인 | 직접 기입 |

“괜찮음” 대신 “합계 6건 일치”, “도착 보장 문장 1곳 수정”처럼 확인한 결과를 적습니다. 모든 항목을 AI에게 재검토하도록 요청할 수 있지만, 중요한 원문과 최종 사용 여부는 업무 책임자가 직접 확인합니다.

## 반복 업무에는 바뀌는 것과 유지할 것을 나눕니다

| 다음에도 유지 | 매번 새로 제공 |
|---|---|
| 독자, 문서 형식, 정책 인용 방식 | 이번 문의 원문과 기간 |
| 미정 항목 표시 기준 | 최신 정책 파일과 변경 사항 |
| 검토 순서와 완료 기준 | 담당자·기한·이번 작업의 실행 범위 |

이번에 찾은 실수는 “출고와 배송 완료를 구분한다”라는 검토 기준으로 프로젝트 지침에 저장할 수 있습니다. 그러나 문의 6건이라는 숫자는 예제 자료의 값이므로 다음 작업의 기본값으로 저장하지 않습니다.

```text
이번 수정 사항을 다음 업무의 검토 기준으로 정리해 줘.
예제 숫자와 이번 담당자는 반복 지침에 넣지 마.
매번 새로 확인할 자료와 질문을 따로 목록으로 만들어 줘.
```

## 예약은 반복 기준을 검증한 다음에 설정하세요

일단 같은 형식으로 새 자료를 넣어 다시 수행해 봅니다. 자료 갱신과 검토가 안정적으로 이어지는지 확인한 뒤 앱이 제공하는 예약 기능을 확인합니다. 예약에는 실행 시각·자료 접근·실패 시 처리·결과 확인 위치를 정합니다. 자동 게시가 꼭 필요하지 않으면 검토할 초안만 생성하는 방식으로 시작할 수 있습니다. [반복 업무 안내](/workflows/reuse/).

## 최종 과제

자신의 업무를 골라 목표, 자료, 지침, 스킬 후보, 업무 순서, 검토표를 한 페이지로 정리합니다. 실제 작은 예제를 수행하고 “확인한 결과”와 “아직 확인하지 못한 부분”을 나누어 기록하세요. [업무별 실습](/cookbook/)에서 시작할 예제를 고릅니다.
