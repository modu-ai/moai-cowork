## 이번 수업에서 배울 내용

업무를 담당자별로 나누고, 어떤 작업을 함께 진행할 수 있는지 판단합니다. 실제 에이전트 실행을 지원하지 않는 환경에서도 같은 역할과 기준으로 순서대로 진행할 수 있습니다.

![분석 후 FAQ와 안내문을 나누어 작성하고 합친 뒤 독립 검토하는 전문가 업무 순서](/infographics/kindle/parallel-ko.png)

분류가 끝난 문의 표와 같은 정책을 FAQ 작성자와 안내문 작성자가 각각 받아 별도 초안을 만듭니다. 그림에서 같은 높이에 놓인 두 작성 작업만 병렬 후보입니다. 결과 파일을 나누고, 두 초안이 모인 뒤 검토를 시작합니다.

점선은 검토 의견이 작성 단계로 돌아가는 길입니다. “영업일 2일 이내 출고”가 “이틀 안에 도착”으로 바뀌었다면 작성자가 정책에 맞춰 고친 뒤 다시 검토합니다. 현재 앱이 별도 에이전트 실행을 지원하지 않으면 같은 역할과 기준으로 순서대로 수행합니다.

## 여러 담당자가 필요한 이유

한 요청에서 모든 일을 처리할 수도 있습니다. 그러나 문의 분류, 고객용 문장 작성, 정책 근거 검토는 서로 확인할 항목이 다릅니다. 업무를 나눌 때는 사람 이름처럼 역할만 붙이지 말고 **각 담당자가 무엇을 받아 무엇을 만드는지** 정해야 합니다. 검토 담당자는 결과를 원문과 비교하고, 근거가 없는 약속을 찾아야 합니다.

## 예제 업무 · 문의 6건을 FAQ와 안내문으로 바꾸기

자료는 [가상 문의 CSV와 정책](/downloads/classroom/)입니다. 배송 문의 3건, 반품 문의 2건, 결제 문의 1건이 있습니다. 정책에는 출고와 반품 절차가 있지만 결제 승인 기준은 없습니다. 따라서 결제 문의는 확인 필요 목록으로 남깁니다.

| 담당 역할 | 스킬 후보 | 입력 | 출력 | 시작 조건 |
|---|---|---|---|---|
| PM | `moai-pm:project` | 목표·자료·환경 | 계획과 미정 목록 | 작업 시작 |
| 분석 | `moai-cs:cs-voc-triage` | 문의 6건 | 유형 표와 원문 ID | 자료 읽기 확인 후 |
| FAQ 작성 | `moai-cs:cs-kb-article` | 유형 표·정책 | FAQ 초안 | 분석 완료 후 |
| 안내문 작성 | `moai-cs:cs-draft-response` | 유형 표·정책 | 고객용 안내문 초안 | 분석 완료 후 |
| 검토 | `moai-cs:cs-quality-audit` | 원문·정책·합친 초안 | 수정 목록 | 두 초안을 합친 후 |

표의 스킬은 설치 후보이며 실제 실행 목록이 아닙니다. PM이 현재 환경에서 사용할 스킬과 에이전트 도구를 먼저 확인해야 합니다. 스킬의 방법을 사용해 역할별로 작업하는 것과 별도 에이전트 프로세스를 실행하는 것도 구분합니다. [OpenAI 하위 에이전트 안내](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Claude Code 하위 에이전트 안내](https://code.claude.com/docs/en/sub-agents).

## 순차와 병렬을 구분하는 기준

FAQ와 안내문은 이미 정리된 같은 유형 표를 받아 각각 별도 결과를 만들 수 있으므로 병렬 후보입니다. 검토는 그 결과를 봐야 하므로 나중에 시작합니다. “모두 동시에”라고 하면 아직 없는 초안을 검토하거나 두 담당자가 같은 파일을 덮어쓰게 될 수 있습니다.

```text
분석 → [FAQ 작성 / 안내문 작성] → 결과 합치기 → 독립 검토 → 수정
```

대괄호 안 두 작업만 독립적입니다. 결과 파일도 `FAQ-초안.md`와 `안내문-초안.md`처럼 분리합니다. 합칠 담당자가 같은 정책 표현과 출처 기준을 적용합니다.

## 실습 요청

```text
가상 문의 6건과 정책으로 FAQ와 안내문 초안을 만들어 줘.
먼저 현재 사용할 수 있는 스킬과 에이전트 기능을 확인해 줘.
각 역할의 입력·출력·완료 기준을 계획에 적어 줘.
문의 분류가 끝난 뒤 FAQ와 안내문을 별도 결과로 작성해 줘.
지원되는 경우 독립된 작성 작업을 병렬로 진행하고,
지원되지 않으면 같은 역할과 기준으로 순서대로 처리해 줘.
합친 뒤 원문과 정책으로 검토하고 결제 정책 누락은 질문해 줘.
실제 게시나 고객 발송은 하지 마.
```

## 모범 결과에서 확인할 것

문의 합계는 6건이고 유형별 합은 `3+2+1=6`이어야 합니다. 배송 안내에는 출고 기준과 배송 완료 시점을 구분해야 합니다. 결제 거절의 원인을 임의로 만들면 검토에서 수정합니다. 각 결과의 근거로 `Q1` 같은 문의 ID와 정책 제목을 남깁니다.

## 담당자가 막히면 어떻게 할까요?

결제 정책이 없으면 결제 답변만 보류하고 배송·반품 FAQ는 작성할 수 있습니다. 인증이 안 되어 실제 문의를 읽지 못하면 제공받은 예제로 진행한 범위를 표시합니다. “전체 완료”라고 묶지 말고 완료한 일, 보류한 일, 다음에 필요한 정보를 따로 기록하세요.

## 확인 문제

검토 담당자에게 초안 작성과 동시에 정책 검토를 맡겨도 될까요?

<details><summary>답안과 해설 보기</summary>

정책 자료 자체의 누락을 살피는 작업은 별도로 할 수 있습니다. 그러나 작성된 초안이 정책에 맞는지 확인하는 검토는 초안이 나온 뒤에 해야 합니다. 같은 “검토”라는 이름이라도 입력이 무엇인지 확인해야 순서를 정할 수 있습니다.

</details>
