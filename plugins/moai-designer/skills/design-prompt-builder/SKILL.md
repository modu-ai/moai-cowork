# design-prompt-builder — UX 작업 프롬프트

사용자의 실제 목표, 대상 화면, 브랜드 자료와 제약을 먼저 확인한다. 직함이나 유명 회사 경력을 꾸며 전문가인 척하지 않는다. 패턴은 작업을 정리하는 참고 틀이며, 하나의 요청에 여러 관점이 필요하면 결합한다.

## 작업 유형

| 요청 | 프롬프트에 담을 핵심 |
|---|---|
| 정보 구조 | 콘텐츠 목록, 이용자의 주요 과업, 탐색 경로 |
| 리서치 | 확인할 가설, 대상자, 질문·관찰 방법 |
| 디자인 시스템 | 기존 브랜드 자산, 필요한 토큰·컴포넌트, 적용 환경 |
| 마이크로카피 | 화면 맥락, 사용자 행동, 브랜드 말투 |
| 온보딩 | 첫 과업, 현재 장애, 성공 판단 기준 |
| 사용성 감사 | 실제 화면·흐름, 관찰 가능한 문제, 개선 우선순위 |
| 대시보드 | 사용자의 결정, 지표 정의·출처, 데이터 상태 |
| 접근성 | 대상 플랫폼, 적용 기준, 검사 가능한 화면·상태 |
| 폼 | 필요한 정보, 오류·회복 흐름, 적용되는 개인정보 조건 |
| 프로토타입 테스트 | 검증할 흐름, 참가자, 과업과 관찰 기준 |

셰이더·3D·오디오·애니메이션 요청에는 해당 매체의 성능·기기·저감모션 제약을 추가한다. 프레임률이나 지연 시간은 근거 없이 보장하지 않고 실제 구현에서 측정한다.

## 진행

1. 사용자가 준 요청과 첨부 자료에서 목표·대상·브랜드·제약·원하는 산출물을 추출한다.
2. 빠진 정보가 결과를 바꾸면 사용 가능한 질문 채널로 짧게 확인한다. 없어도 진행 가능한 정보는 `[확인 필요]`로 남긴다. 매출, 전환율, 이탈률, 사용성 테스트 결과를 만들어 넣지 않는다.
3. 필요한 작업 유형을 고른다. 모든 디자인 시스템에 다크 모드나 전체 컴포넌트를 강제하지 않는다. 화면에 필요한 범위를 정한다.
4. 다음 형식으로 바로 쓸 수 있는 프롬프트를 만든다.

```text
목표: [사용자가 이루려는 일]
대상: [사용자와 화면·서비스]
자료: [제공된 브랜드 파일·화면·데이터·URL]
제약: [플랫폼·접근성 기준·기술·일정 중 실제로 확인한 것]
작업: [요청에 필요한 디자인·분석 단계]
산출물: [사용자가 요청한 결과 형식과 범위]
검증: [구현 후 또는 실제 사용자와 확인할 항목]
미확인: [결정에 필요한 질문]
```

5. Claude Design을 지정한 사용자에게는 현재 사용 가능한 Claude Design 채팅이나 핸드오프 경로에서 이 프롬프트와 자료를 전달하도록 안내한다. ChatGPT Work에서 계속 작업할 때는 같은 프롬프트를 현재 대화에 적용한다. 외부 서비스에 이미 업로드·테스트·내보내기를 했다고 주장하지 않는다.

## 접근성 요청

적용 지역·제품·플랫폼과 요구 기준을 먼저 확인한다. 웹이라면 [WCAG 2.2](https://www.w3.org/TR/WCAG22/)의 관련 성공 기준을 참고할 수 있다. 색 대비 계산, 키보드·스크린리더 점검, 실제 화면 테스트는 각각 수행한 경우에만 결과를 적는다. 프롬프트만 작성한 단계에서 준수나 인증을 선언하지 않는다.

## 카피와 사용자 데이터

실제 제품 문구, 가격, 성과, 후기와 법적 동의 내용은 사용자 자료에서 가져온다. 없는 값은 예시로 표시하거나 확인 요청으로 남긴다. 한국어 문구에 영어 단어 수 제한을 기계적으로 적용하지 않는다. 브랜드가 사용하는 폰트나 색을 근거 없이 금지하지 않는다.

## 출력

- 선택한 작업 유형과 선택 이유
- 복사해 사용할 프롬프트
- 미확인 정보와 적용 전 확인할 항목

관련 스킬: `design-brief`(브리프 정리), `design-gui-guide`(컴포넌트 사용성), `design-slop-check`(결과 카피 검토).
