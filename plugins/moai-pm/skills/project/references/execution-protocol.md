# 스킬 체인 실행

사용자 요청에 필요한 맥락과 현재 호스트의 스킬 노출 상태를 확인하고, 요청한 산출물을 만든다. 이미 충분히 구체적인 요청에는 인터뷰를 반복하지 않는다.

## 실행 순서

1. 대화로 충분한 요청인지, 스킬 실행이나 파일 생성이 필요한지 판단한다.
2. 부족한 핵심 정보만 `context-collector.md`에 따라 묻는다. 질문 도구의 스키마는 현재 호스트에서 확인한다.
3. 산출물과 완료 기준, 필요한 스킬 체인을 간단히 정리한다. 사용자가 이미 작업을 지시했다면 별도 승인 절차를 되풀이하지 않는다. 외부 게시·전송 등 승인 범위가 불명확한 행동은 결과를 준비한 뒤 해당 행동만 확인한다.
4. 현재 노출된 스킬과 단계별 선행 관계·쓰기 소유권을 확인한다. 허용된 독립 단계는 병렬, 의존 단계·같은 경로·외부 변경은 순차 실행한다. 중간 결과와 다음 단계 입력을 대조하고 합류한다. 스킬이 없으면 해당 단계와 그 의존 단계만 보류하고 대체 경로를 제시한다.
5. `quality-evaluator.md`의 파일·형식 검사와 `evaluation-protocol.md`의 의미 검사를 수행한다. 텍스트는 프로젝트의 한국어 품질 체인을 적용한 뒤 사실과 원문을 다시 대조한다.
6. 산출물, 실제 확인 결과, 미확인 항목과 후속 조치를 전달한다. 파일을 만들었다면 다시 열어 확인한다.

복합 작업은 필요한 만큼 깊이 있게 검토한다. `ultrathink` 같은 특정 호스트 명령이 없어도 동일한 분석 절차를 진행한다.

## 의존성·소유권·합류

전체 정의는 `.moai/config.json`의 `workflows`에 보존한다. 단계마다 `id`, `depends_on`, `skills`, `agent`, `operation`, `write_set`, `outputs`, `completion_criteria`, `status`, `evidence`를 둔다. 반복 작업의 전문가는 `expert-contract.md`로 연결한다. 이름·버전·digest만으로 호출 가능을 판정하지 않는다.

- `host.subagents`와 `delegation_authorized`, 실제 동시 실행 한도를 확인한다. 상위 사용자·호스트 지침이 분업을 허용할 때만 하위 에이전트를 호출한다. 미확인·미지원이면 순차로 같은 계약을 실행한다.
- 서로 다른 자료 조사·계산·독립 산출물은 병렬 후보다. 같은 파일·부모 경로·glob을 공유하는 쓰기는 직렬화하거나 한 소유자가 통합한다. 외부 상태 변경은 계정·자원·operation·요청의 권한을 확인하고 직렬화한다.
- 부모는 전문 작업에 목표·입력·담당 경로·허용 도구·완료 기준을 전달한다. 담당자는 타인의 변경을 되돌리지 않고 자신의 결과·근거·누락 정보를 반환한다.
- 합류 단계는 모든 필수 선행 결과를 확인하고 사실·형식·입출력 충돌을 해소한 뒤 진행한다. 한 결과가 실패하면 의존 단계는 보류하고 무관한 결과는 보존한다.
- `pending/running/blocked/completed/failed`와 질문·증거·산출물 경로를 저장한다. 실행하지 않은 단계를 completed로 표시하지 않는다. 재개 시 실제 파일·도구 상태를 다시 확인한다.

`scripts/project_contract.py validate --config <설정> --root <작업 폴더>`로 순환·미노출 스킬·경로·완료 증거를 검사한다. `plan --config <설정>`은 병렬 묶음과 차단 단계를 계산할 뿐 실제 업무를 실행하지 않는다. 실행 상태는 실제 도구 결과로 갱신한다.

## MCP 변경 작업

계정 파일·OAuth 회전 파일의 프로젝트별 배선과 큰 스키마 측정은 `account-bindings.md`를 따른다.

프로젝트 설정에는 비밀값 대신 계정·상점 식별자와 credential 참조를 저장한다. 선언·tools/list·인증·실제 호출을 별개로 기록한다. 혼합 조회/변경 도구는 읽기 전용으로 가정하지 않는다. 도구 annotations는 인증이나 사용자 권한을 대신하지 않는다.

변경 전 대상 계정·자원·operation·완료 기준을 확인한다. 요청이 이미 그 작업을 승인했다면 같은 확인을 반복하지 않는다. 모호한 실패는 실제 상태를 재조회하고, 서비스가 지원하는 멱등키를 재사용한다. 지원 여부를 확인하지 않은 operation을 멱등이라고 표시하지 않는다. 부분 실패는 항목별 결과와 재시도 범위를 남긴다.

## 검증 깊이

| 등급 | 시작점 | 필요한 증거 |
|---|---|---|
| QUICK | 간단한 정리·재구성 | 입력과 결과의 대응, 파일을 만들었다면 존재·내용 확인 |
| NORMAL | 일반 문서·카피·기획 | 요청 항목, 형식, 사실 주장과 출처 대조 |
| DEEP | 법률·계약·개인정보·세무·재무·의료·규제·외부 발송 등 | 현재 공식 원출처, 관할·날짜, 계산·실행 결과, 미확인 범위 |

여러 플러그인을 썼다는 사실만으로 DEEP이 되는 것은 아니다. 사용자가 빠른 답을 원해도 높은 위험의 근거 검증을 생략하지 않는다. 설명 분량은 줄일 수 있으나 검증 범위는 실제 위험에 맞춘다. 키워드가 없어도 결과의 위험이 크면 DEEP으로 올린다.

외부 사실은 최신성이 중요한 경우 검색하거나 공식 문서를 확인한다. 검색 횟수를 미리 정해 채우지 않는다. 관련 근거가 충분해지면 멈추고, 근거가 부족하면 필요한 만큼 더 찾는다. 출처 URL이 적혀 있다는 사실만으로 그 내용이 주장을 뒷받침한다고 판정하지 않는다.

## 실패 처리

스킬·도구 호출 실패는 호출 여부와 오류를 확인한다. 부작용이 있는 작업이 애매하게 실패했다면 현재 상태를 먼저 조회한 뒤 중복 실행 여부를 결정한다. 대체 경로가 있어도 품질·권한·개인정보 조건이 달라지면 이를 명시한다. 결과물을 만들 수 없는 경우 현재까지 검증한 부분과 막힌 부분을 구분해 보고한다.
