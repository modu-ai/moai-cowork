# UX 디자인 검토

사용자가 제공한 화면, 와이어프레임, 프로토타입, 실제 제품 중 접근 가능한 자료를 먼저 확인한다. 화면이 없고 설명만 있다면 설계 검토와 확인 질문을 제시할 수 있지만 특정 UI 결함을 관찰한 것처럼 쓰지 않는다.

## 검토 절차

1. **대상과 범위**: 플랫폼, 주요 사용자, 핵심 작업, 검토할 화면·상태와 접근 가능한 자료를 기록한다.
2. **사용성**: 화면에서 관찰한 단계·오류 복구·상태 표시·용어 일관성을 점검한다. 휴리스틱은 문제를 설명하는 도구로 사용하며 모든 항목을 억지로 채우지 않는다.
3. **접근성**: 웹 콘텐츠라면 적용할 [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/) 성공 기준과 수준을 확인한다. 스크린샷만으로 키보드 동작, 스크린리더 출력, 실제 대비, 코드 구조의 적합성을 확정하지 않는다. 해당 검사는 실행 가능한 제품과 도구가 있을 때 수행한다.
4. **플로우**: 제공된 경로에서 완료·실패·되돌아가기·빈 상태를 살핀다. 사용자 행동 데이터나 테스트 기록이 없다면 이탈 원인과 전환율 영향은 가설로 둔다.
5. **개선안**: 관찰 근거, 영향받는 작업, 수정 제안, 검증 방법을 짝지어 쓴다. 긴급도는 실제 영향과 사용자 제약을 바탕으로 정하고 근거 없는 RICE 점수나 고정 기간 로드맵은 만들지 않는다.

## 출력 틀

| 화면·작업 | 관찰 내용과 근거 | 관련 기준 | 영향과 불확실성 | 제안 | 확인 방법 |
|---|---|---|---|---|---|

화면이 없으면 관찰 결과 표 대신 필요한 화면·상태·사용자 자료 목록과 검토 계획을 낸다. 접근성 검토는 관찰한 항목, 미검사 항목, 적용 기준을 분리한다. 법적 준수 판정은 해당 관할·제품의 실제 요구와 검증 범위를 확인한 뒤 별도로 다룬다.

사용자 인터뷰·설문·VOC 분석은 `moai-coworker:collab-ux-research`, 요구사항 문서화는 `moai-coworker:collab-spec`을 사용한다. 문체를 다듬을 때도 결함의 근거와 미검사 표시를 지우지 않는다.
