# 자체 MCP 서버 지연 실행

최종 수정: 2026-10-09

호스트가 stdio 연결마다 서버를 시작하더라도, 도구 목록 조회만으로 실제 서버와 MCP SDK를 올리지 않도록 하는 공용 런처입니다. 경량 프록시 프로세스는 연결마다 남습니다. 세션 간 서버 공유나 프로세스 수 전체의 상한을 제공하지는 않습니다.

## 동작

1. 초기화·도구 목록·빈 리소스 및 프롬프트 목록·ping은 배포된 `mcp-catalog.json`으로 응답합니다. 이때 백엔드는 실행하지 않습니다.
2. 첫 `tools/call`에서 백엔드 하나를 시작합니다. 원래 클라이언트 정보·기능·협상한 프로토콜 버전을 재생하고, 실제 초기화 응답과 도구 목록을 스냅샷과 대조합니다.
3. 일치할 때만 대기 중인 호출을 전달합니다. 이후 취소·진행 알림·서버 요청·클라이언트 응답을 전달합니다. 동시에 호출이 들어와도 연결당 백엔드는 하나입니다.
4. 연결 종료·SIGINT·SIGTERM·초기화 실패 때 자신이 시작한 백엔드를 회수합니다. 파이프 쓰기는 별도 큐로 처리하므로 큰 요청이나 읽히지 않는 응답이 종료 처리를 막지 않습니다.

백엔드는 첫 호출 이후 연결이 끝날 때까지 유지합니다. 호출마다 종료하면 저장에 실패한 갱신 토큰 등 메모리에 남은 상태를 잃을 수 있습니다. 백엔드 연결이 끊긴 호출은 자동 재전송하지 않습니다. 게시·주문 변경·과금 요청이 이미 처리됐을 가능성이 있기 때문입니다.

이벤트·초기화 대기·양방향 쓰기 큐는 직렬화한 메시지 기준 256MiB·64개 예산을 공유합니다. 큐 사이에 예약을 이전하고 실제 쓰기가 끝난 뒤 해제합니다. 진행 중 요청도 ID만 최대 64개 보관합니다. 예산이 비어 있으면 단일 대형 메시지는 허용하며, 추가 메시지로 예산을 넘기면 연결을 실패 처리하고 자식을 정리합니다. 종료 신호와 EOF는 예산이 찬 상태에서도 처리합니다. 단일 대형 메시지와 파싱 중 일시 메모리 때문에 이 값이 프로세스 RSS의 절대 상한은 아닙니다.

## 적용 범위와 정합성

대상은 IP·OpenAI·Smartstore·Imweb·Cafe24·Threads 자체 서버입니다. 기존 서버 이름과 도구 이름, 인증 환경변수는 유지합니다. 제3자 서버와 별도 저장소의 개인용 광고 서버에는 자동 적용하지 않습니다.

스냅샷은 임시 사용자 홈과 허용 목록 환경변수로 격리한 실제 SDK 진입점에서 생성합니다. 도구 실행이나 외부 서비스 API 호출 없이 초기화·목록 응답만 수집하며 입력·출력 스키마, 동작 힌트와 instructions를 보존합니다. 런타임과 생성기 모두 `uv run --locked`로 서버의 `uv.lock`을 사용합니다.

동적 목록·구독·비어 있지 않은 리소스 및 프롬프트·실험 기능·목록 페이지가 생기면 생성기가 거부합니다. 그런 기능을 추가할 때는 프록시 지원 범위를 함께 검토하거나 해당 서버를 직접 실행하도록 되돌려야 합니다.

정본은 이 폴더의 `mcp_lazy.py`입니다. 각 플러그인의 `mcp-launch/mcp_lazy.py`는 생성된 사본이므로 직접 수정하지 않습니다. 매니페스트 수정은 `.mcp.json`과 `.codex-plugin/plugin.json`에 각각 반영하고 공통 `mcp.json`은 기존 생성기로 갱신합니다.

macOS·Windows 공통 개발 명령:

```text
uv run --python 3.11 python scripts/sync-mcp-core.py
uv run --python 3.11 python scripts/sync-mcp-lazy.py
uv run --python 3.11 python scripts/sync-mcp-lazy.py --check
uv run --python 3.11 python scripts/sync-mcp-lazy.py --verify --server moai-mcp-ip
uv run --python 3.11 --with pytest pytest -q plugins/_shared/mcp-lazy/test_mcp_lazy.py
```

`--check`는 백엔드를 시작하지 않고 소스·lockfile의 digest와 프록시 사본을 검사합니다. digest는 체크아웃의 CRLF 차이를 정규화합니다. `--verify`는 잠긴 SDK의 실제 응답까지 비교합니다. CI는 기존 OS별 서버 작업에서 해당 서버만 검증합니다.

## 종료 보장의 한계

POSIX에서는 자신이 만든 프로세스 그룹을 정리합니다. Windows에서는 제한 시간을 둔 `taskkill /T /F`를 사용합니다. SIGKILL로 프록시 자체를 강제 종료한 경우, 자식이 스스로 그룹을 벗어난 경우, Windows에서 그룹 부모가 먼저 사라진 경우의 전체 자손 회수는 보장하지 않습니다. 호스트가 세션을 유지하며 stdio 연결도 열어 둔 상태는 연결 종료로 판별할 수 없습니다.

테스트는 미사용 백엔드 미기동, 첫 호출 중복 방지, 초기화·스키마 불일치, 취소·진행 알림, 서버 요청, 대용량 데이터, EOF·신호 및 파이프가 막힌 상태의 종료를 확인합니다. 실제 데스크톱 앱 설치·계정 인증·유료 API 성공은 별도 검증 대상입니다.
